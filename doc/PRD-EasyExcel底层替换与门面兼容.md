# Excel 工具库底层引擎替换 产品需求文档

**文档类型**：产品需求文档  
**适用对象**：使用本 Excel 工具库的业务系统开发、库维护研发、测试

| 版本号 | 更新时间 | 备注 |
|--------|----------|------|
| v1.0 | 2026-05-19 | 初版：底层切换为 EasyExcel，门面高度兼容 |

**本文档范围**：本文档包含 3 个子需求，需一并交付：

- **主需求**：在不动「怎么用」的前提下，把读写 Excel 的底层引擎换掉（约 200 行）
- **子需求 1**：导入能力底层替换（见第二节 2.1）—— 不先换导入，现有上传校验、回写结果表都无法用
- **子需求 2**：导出能力底层替换（见第二节 2.2）—— 不先换导出，现有下载报表、多表导出都无法用
- **子需求 3**：门面兼容与升级约束（见第二节 2.3）—— 不先定规则，无法判断「算不算改坏了」

## 一、这是什么

把本 Excel 工具库内部「读写文件」的实现，从 **Hutool Excel** 换成 **EasyExcel**。  
**门面层**（导入入口、导出入口、链式配置、导入结果报告、Spring 启用注解等）**尽量不改名、不改用法、不改调用顺序**。

| 场景 | 换完后应达到的效果 |
|------|-------------------|
| 已有项目按文档写导入 | 不用改业务代码，导入校验、错误回写、JSON 报告行为与现网一致 |
| 已有项目按文档写导出 | 不用改业务代码，单表/多表/多级表头/条件着色与现网一致 |
| 新接入项目 | 仍按现有 README 三步完成导入导出，不额外学一套 API |
| 库维护方 | 底层统一为社区更常用的 EasyExcel，后续修 bug、跟版本更安全 |

**术语**：

- **门面层** = 业务开发直接调用的那一层（创建导入/导出、加列、读、写、下载）
- **底层引擎** = 真正打开 xlsx、按行/按格读写的实现
- **高度兼容** = 同一套业务代码、同一份模板、同一份导出样式，换库版本后结果肉眼和业务规则上一致

## 二、前置功能

### 2.1 导入能力底层替换（刚需子需求）

> **重要**：本库一半价值在「上传校验 + 把错误写回 Excel 或返回 JSON」。导入底层不换，主需求无法验收。

**什么是导入底层替换**：用户上传的 xlsx/csv，在门面配置不变的情况下，由 EasyExcel（及必要的配套能力）完成「按表头逐行读」和「按指定格子读」。

**必须继续支持的能力**（与当前 README 一致）：

- 按**表头名称**绑定列，支持类型转换（数字、日期、金额等内置转换器）
- 按**单元格位置**读取（如 B1、或第几行第几列）
- 多工作表：按序号切换不同 sheet 分别导入
- 模板校验：表头/必填格与模板不一致时能识别并记入导入报告
- 行级错误收集：哪一行失败、失败原因；支持「只收集错误、不攒成功行」等配置
- 导入结束后：**把失败原因写回原表新增一列**，或直接 **返回结构化导入报告**（给接口 JSON 用）
- 大文件：仍受「最多同时跑几个导入任务」限制，避免内存打满
- CSV 上传：仍能先转成 xlsx 再走同一套导入流程（且转换结果文件路径必须正确）

**约束规则**：

- 门面上的「选第几个 sheet、从第几行开始当数据、读到第几行结束」等范围设置，换引擎后行为不变
- 「空行跳过」「模板列必须存在」「某列允许为空」「某列必填」等开关，换引擎后结论不变
- 自定义业务异常文案机制（通过启用注解注册）继续生效
- 同一 sheet 内用「重置读取器」读第二段表格的能力保留；仍不参与「生成回写结果文件」的规则不变

**举例说明**：

```
运营上传《商品导入模板.xlsx》
开发代码：创建导入 → 选第 1 个 sheet → 绑定「产品编码」「价格」→ 读每一行入库
         ↓
换引擎前：第 3 行价格填了文字 → 第 3 行记失败，下载回来的表第 3 行「导入结果」列有原因
换引擎后：同上，不能变成「整表报错」或「静默跳过」
```

### 2.2 导出能力底层替换（刚需子需求）

> **重要**：报表导出、多级表头、多 sheet 是门面层最复杂的一块；导出底层不换，兼容承诺不成立。

**什么是导出底层替换**：生成 xlsx 时，门面仍用「加表头 → 写列表 → 输出下载」，底层由 EasyExcel 承担流式写入与样式落盘。

**必须继续支持的能力**：

- 基础导出：多列、多行数据
- **多级表头**（用「父级::子级」这种方式描述层级）
- **多工作表**：一个文件里多个 sheet，且 sheet 顺序与创建顺序一致
- **条件单元格样式**：满足条件才上色（如亏损标橙、盈利标绿）
- 同一 sheet 内**先写一段表再写下一段**（重置写入位置、可只写表头不写数据）
- 限制写入行范围（只写模板允许的数据区）
- 大列表导出：仍能分批写，不因数据量大而整表进内存

**约束规则**：

- 表头合并（横向、纵向）后的视觉效果与现版一致，不允许表头错位、重复合并
- 先 `write` 空列表只出表头、再追加 `write` 数据的行为不变
- 切换 sheet 时必须按顺序初始化（不能跳过前一个 sheet 直接写后面的）
- 下载文件名、临时文件清理策略与现版一致

**举例说明**：

```
财务导出《月度报表》：两级表头 + 两个 sheet（明细、汇总）
         ↓
换引擎后：打开文件仍能看到合并好的表头、两个 sheet 名称与顺序不变、条件着色仍在对应单元格上
```

### 2.3 门面兼容与升级约束（刚需子需求）

> **重要**：没有这条，无法判断「换引擎」是否算交付完成。

**什么是门面兼容**：业务项目里已经写好的导入/导出代码，**在不大改的前提下**升级库版本后仍能编译、仍能跑通主流程。

**兼容范围（必须保持）**：

| 类别 | 要求 |
|------|------|
| 入口与链式调用 | 创建导入/导出、切换 sheet、加列/加转换、读、写、response 下载 —— 调用顺序与参数含义不变 |
| 导入配置项 | 统一导入配置（快速失败、最多记多少行错、是否收集成功数据等）语义不变 |
| 导入结果 | 结构化导入报告（成功条数、失败行、全局错误类型）字段含义不变 |
| Spring 集成 | 启用注解、并行导入上限、临时文件保留分钟数 仍生效 |
| 内置转换 | 字符串、整数、长整型、金额、日期、日期时间 等解析规则与现版一致 |
| 对外依赖 | 业务侧 **不需要** 为了用本库再去单独引入 Hutool Excel；是否保留其他 Hutool 工具包不在本 PRD 范围 |

**允许的变化（需写进升级说明，不算兼容失败）**：

- 库版本号按 **次版本或主版本** 提升（因底层引擎变更）
- 打包体积、依赖树与现版可能不同
- 极端大文件下的耗时、内存曲线允许有差异，但 **不能 OOM、不能丢数据**
- 内部实现类名可能调整，但 **不作为对外承诺**

**明确不做（本期）**：

- 不重做门面 API 设计（不顺手「顺便」改名、拆包）
- 不新增「注解驱动实体导入」等与现门面并列的第二套用法（可放后续版本）
- 不要求业务把现有模板改成 EasyExcel 注解模型

## 三、典型场景

### 场景 1：标准导入 + 错误回写（最常见）

```
业务操作：运营上传填好的 Excel → 系统校验并入库 → 浏览器下载带「导入结果」列的文件
开发写法：保持不变（创建导入 → 配列 → 逐行处理 → response 下载）
         ↓
结果：失败行有原因；成功行结果列可为空（与 v2.3.1+ 行为一致）；表头、数据列不被破坏
```

### 场景 2：接口只要 JSON，不要回写文件

```
业务操作：小程序/前后端分离上传 → 接口返回 { 成功数、失败行列表 }
开发写法：保持不变（读完后取结构化导入报告）
         ↓
结果：JSON 字段含义与现版一致；fail-fast、最多记 100 条错等预设仍可用
```

### 场景 3：按固定格子读配置（非表格式）

```
业务操作：模板第 1 页只有几个关键参数格（系统名、版本号等）
开发写法：保持不变（切换「按格子读」→ 绑 B1、D1 等）
         ↓
结果：读到的值与 Excel 里肉眼看到的一致；必填格为空仍报缺项
```

### 场景 4：多级表头 + 多 sheet 导出

```
业务操作：一次下载含「销售明细」「汇总」两个 sheet，表头有两层合并
开发写法：保持不变（多次 switch 新 sheet → addTitle → write → response）
         ↓
结果：WPS/Office 打开版式正常，无表头重叠、无数据写到表头区
```

### 场景 5：大表导入（并发与内存）

```
业务操作：同时多人导入万行级文件
系统配置：启用注解里限制「最多 2 个导入并行」
         ↓
结果：第 3 个导入等待或受限；换引擎后仍不能因单文件导致进程内存爆掉
```

### 场景 6：CSV 当 Excel 传

```
业务操作：用户上传 .csv
         ↓
结果：库内先转成 xlsx 再按导入流程走；转换后的文件能被正常打开且行数一致
```

## 四、怎么用

**谁可以**：

- **业务系统开发**：按现有 README 写导入导出，升级库版本即可，无需学新 API
- **库维护研发**：按本 PRD 验收后发布新版本，并提供「升级说明」列出允许差异
- **测试**：用 README 全部场景 + 现网真实模板做回归

**怎么操作（对使用方）**：

1. 升级 Maven 依赖到新版本号  
2. 跑一遍现有导入导出接口自动化或手工用例  
3. 对比：同模板、同数据，导入报告与导出文件是否与升级前一致  
4. 若仅依赖「旧版每行都写导入成功文案」的展示习惯，需知 v2.3.1 起成功行结果列已可为空 —— 与本次换引擎无关，但回归时要按现行规则测  

**怎么操作（对交付方）**：

1. 先完成导入底层替换并通过场景 1～3、5、6  
2. 再完成导出底层替换并通过场景 4  
3. 全量回归后发布，README 中「基于 Hutool」的描述改为「基于 EasyExcel」，并附升级说明

## 五、关键规则

### 规则 1：门面优先，行为对齐

- 以当前 README 与现网主流程为准，不以新引擎的默认行为为准
- 出现差异时，改底层适配层，而不是让业务改调用方式

**举例**：新引擎默认把日期读成另一种格式 → 应通过内置日期转换器修回与现版相同，而不是要求业务改模板。

### 规则 2：兼容不是「字节级相同」

- 允许：列宽自动计算略有差别、极冷门函数格/富文本未覆盖  
- 不允许：少行、错列、表头名对不上、该报错不报错、该回写没回写

**举例**：同一导入文件，失败行号集合与失败原因集合应与现版一致；允许 Excel 打开后列宽差 1～2 个字符。

### 规则 3：高风险能力单独立项验收

以下能力换引擎难度高，**必须单独列用例**，不能只做「冒烟一条」：

- 按指定格子读取（非整表按行）
- 多级表头合并与续写（reset 同 sheet 第二段表）
- 条件样式导出
- CSV 转 xlsx 再导入
- 多 sheet 顺序与隐藏 sheet 场景（若现网有）

### 规则 4：依赖与版本

- 底层以 **EasyExcel** 为唯一 Excel 读写引擎（读取、写入大文件）
- 可与现有 **POI** 能力共存的部分（如结果回写、workbook 级操作）保留，但不得再依赖 Hutool 的 Excel 读写
- 发布版本号变更须在 release note 写明，便于业务评估升级窗口

### 规则 5：缺陷修复一并纳入

- 已知问题：CSV 转 xlsx 时「生成路径」与「实际写入文件」不一致 —— 本期必须修掉，作为交付门槛之一

## 六、最终预期标准

**门面兼容**

- [ ] 现有 README 中「导出」全部示例在不改代码的情况下编译通过且文件可正常打开
- [ ] 现有 README 中「导入」全部示例在不改代码的情况下编译通过且结果符合现行规则
- [ ] 启用注解配置的「最大并行导入数」「临时文件保留分钟」仍然生效

**导入**

- [ ] 按表头导入：列绑定、必填/可空、空行过滤、模板列校验与现版结论一致
- [ ] 按格子导入：指定格子的值与 Excel 一致，必填格校验有效
- [ ] 导入失败时，回写文件或 JSON 报告中的行号、原因与现版一致（允许文案标点差异，不允许漏行）
- [ ] 大文件导入在配置的并发限制下不发生 OOM
- [ ] CSV 上传后能完成导入，且行数与源 CSV 一致

**导出**

- [ ] 单级表头、多级表头导出版式正确，合并单元格无错位
- [ ] 多 sheet 导出：sheet 数量、名称、顺序正确
- [ ] 条件样式：满足条件的行仍显示对应底色/样式
- [ ] 大列表导出可完成，不因数据量增大而失败

**引擎与交付**

- [ ] 业务项目无需再为 Excel 读写单独引入 Hutool Excel
- [ ] 提供升级说明：版本号、兼容范围、已知差异、CSV 修复说明
- [ ] 全量自动化或手工回归记录可追溯到本 PRD 第六节每一条
